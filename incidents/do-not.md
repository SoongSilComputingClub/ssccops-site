# 하면 안 되는 조치

급할 때 하기 쉽지만 되돌릴 수 없거나 장애를 키우는 조치입니다. 시스템 담당자가 관리 화면에서 조치하기 전에, 개발자가 급히 코드를 고치기 전에 한 번 확인합니다.

## 되돌릴 수 없는 것

- **DB 스키마가 바뀐 릴리즈를 서버 이미지만 이전 버전으로 되돌리지 않습니다.** 이미지를 되돌려도 DB 변경(Flyway 마이그레이션)은 되돌아가지 않습니다. 이전 버전의 서버가 새 스키마에서 실행되어 시작하지 못하거나 일부 기능이 잘못 동작할 수 있습니다. 되돌리기 전에 서버 GitHub 릴리즈의 «배포 시 주의»와 PR의 «스키마 변경» 칸에서 그 릴리즈에 스키마 변경이 있었는지 확인합니다.
- **이미 적용된 마이그레이션 파일을 고치거나 지우지 않습니다.** 고쳐야 하면 다음 번호로 새 파일을 씁니다. 자세한 규칙은 [데이터베이스와 스키마 변경](/contributing/server/database)에 있습니다.
- **Supabase 프로젝트를 지우거나 새로 만들어 바꾸지 않습니다.** 앱 DB와 로그인 계정이 모두 그 프로젝트에 있습니다. 일시정지된 프로젝트는 Resume project로 복구합니다.
- **웹 푸시 키(VAPID)를 바꾸지 않습니다.** 바꾸면 회원 기기에 등록된 푸시 구독이 모두 무효가 됩니다.

## 장애를 키우는 것

- **readiness가 DOWN일 때 서버 재시작만 반복하지 않습니다.** 원인이 DB에 있으면 서버를 다시 시작해도 해결되지 않습니다. [장애가 발생한 곳 확인하기](check-status.md)부터 합니다.
- **Supabase 관리 화면의 SQL 편집기로 테이블을 만들지 않습니다.** 그렇게 만든 테이블에는 Supabase 기본 권한이 붙어, 웹 화면 코드에 포함된 공개 키로도 읽을 수 있게 됩니다. 스키마는 항상 마이그레이션 파일로 바꿉니다.
- **헬스체크가 사용하는 주소를 코드에서 먼저 바꾸지 않습니다.** Coolify의 헬스체크와 외부 감시 서비스가 그 주소로 서버 상태를 확인합니다. 코드를 먼저 바꾸면 새 버전이 정상 판정을 받지 못해 배포가 실패합니다. 헬스체크와 외부 감시 설정의 주소를 먼저 바꾸고 코드를 머지합니다.
- **배포 성공 표시만 보고 복구가 끝났다고 알리지 않습니다.** CI와 배포 워크플로가 성공으로 표시돼도 새 버전이 배포되지 않았을 수 있습니다. [확인 주소](check-status.md#확인-주소)에서 실행 중인 커밋을 확인합니다.

## 공개 레포에 남기면 안 되는 것

server, web, site 레포의 이슈와 PR은 누구나 읽을 수 있고, 내용을 고쳐도 수정 이력이 남습니다. 장애 이슈를 쓸 때 다음을 넣지 않습니다.

- 토큰, 키, 비밀번호, 환경변수의 값. 이름은 적어도 됩니다
- 관리 화면 주소, 서버 IP와 포트, 서버 구성
- 회원 실명, 학번, 연락처. 로그와 스크린샷도 마찬가지입니다
