# 하면 안 되는 조치

급할 때 손이 가기 쉽지만 되돌릴 수 없거나 장애를 키우는 조치입니다. 시스템 담당자가 관리 화면에서 조치하기 전에, 개발자가 급히 고치기 전에 한 번 봅니다.

## 되돌릴 수 없는 것

- **DB 스키마가 바뀐 릴리즈를 서버 이미지만 옛 버전으로 되돌리지 않습니다.** DB 변경(Flyway 마이그레이션)은 이미지를 되돌려도 따라 돌아가지 않습니다. 옛 서버가 새 스키마 위에서 돌게 되어 부팅이 멈추거나 일부 기능이 틀리게 동작할 수 있습니다. 되돌리기 전에 그 릴리즈에 스키마 변경이 있었는지 서버 GitHub 릴리즈의 «배포 시 주의»와 PR의 «스키마 변경» 칸을 봅니다.
- **이미 적용된 마이그레이션 파일을 고치거나 지우지 않습니다.** 고쳐야 하면 다음 번호로 새 파일을 씁니다. 자세한 규칙은 [데이터베이스와 스키마 변경](/contributing/server/database)에 있습니다.
- **Supabase 프로젝트를 지우거나 새로 만들어 갈아 끼우지 않습니다.** 앱 DB와 로그인 계정이 모두 그 프로젝트에 있습니다. 일시정지는 복원(Restore)으로 풉니다.
- **웹 푸시 키(VAPID)를 바꾸지 않습니다.** 바꾸는 순간 회원 기기에 등록된 푸시 구독이 모두 무효가 됩니다.

## 장애를 키우는 것

- **readiness가 DOWN인데 서버 재시작만 거듭하지 않습니다.** 원인이 DB면 다시 켜도 같은 상태로 돌아옵니다. [어디가 멈췄는지 가르기](check-status.md)부터 합니다.
- **DB 관리 화면의 SQL 편집기로 테이블을 만들지 않습니다.** 그렇게 만든 테이블에는 Supabase 기본 권한이 붙어, 웹에 실린 공개 키로 읽힙니다. 스키마는 언제나 마이그레이션 파일로 바꿉니다.
- **서버가 바깥에서 확인받는 주소를 코드에서 먼저 바꾸지 않습니다.** 배포 도구의 헬스체크와 외부 감시가 그 주소를 봅니다. 코드를 먼저 바꾸면 새 버전이 정상으로 판정받지 못해 배포가 실패합니다. 그쪽 설정을 먼저 옮기고 코드를 머지합니다.
- **배포 성공 표시만 보고 끝났다고 알리지 않습니다.** CI와 배포 워크플로가 초록이어도 새 버전이 뜨지 않았을 수 있습니다. [확인 주소](check-status.md#확인-주소)의 커밋으로 확인합니다.

## 공개 레포에 남기면 안 되는 것

server, web, site 레포의 이슈와 PR은 누구나 읽고, 고쳐도 수정 이력이 남습니다. 장애 이슈를 쓸 때 다음을 넣지 않습니다.

- 토큰, 키, 비밀번호, 환경변수의 값. 이름은 괜찮습니다
- 관리 화면 주소, 서버 IP와 포트, 서버 구성
- 회원 실명, 학번, 연락처. 로그와 스크린샷도 같습니다
