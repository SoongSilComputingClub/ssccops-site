# 지난 사건에서 배운 것

2026년 8월부터 운영에 영향을 준 사건을 모아 보면 비슷한 유형이 반복됩니다. 반복된 유형별로 실제 사례, 재발 방지 조치, 다시 발생했을 때 확인할 곳을 정리합니다.

## 오류 없이 잘못된 값이나 화면이 나올 수 있다

- **사례**: 하위 업무의 승인자 권한 값이 운영 DB에서 모두 비어 최고관리자도 승인하지 못했습니다. 컬럼 이름을 바꿨는데 자동 스키마 갱신이 이를 새 컬럼 추가로 처리해, 값이 옛 컬럼에 남았습니다. 공유 UI 패키지를 만든 뒤 세 앱의 여백과 배지가 사라졌는데 타입 검사, 린트, 빌드는 모두 통과했습니다. 모바일 공개 웹에서 메뉴가 열리지 않았는데 데스크톱에서는 문제가 없었습니다.
- **재발 방지 조치**: 스키마는 마이그레이션 파일로만 바꾸고, 서버가 시작할 때 DB 스키마가 코드와 맞는지 검사해 다르면 시작을 멈춥니다. 코드값(enum)과 DB 제약 조건이 서로 맞는지도 테스트로 확인합니다.
- **다시 발생하면**: 오류가 없다고 정상은 아닙니다. 화면을 직접 열어 보고, 데스크톱과 모바일을 모두 확인합니다.

## 배포가 실패해도 CI는 성공으로 표시될 수 있다

- **사례**: 서버 dev 배포가 다섯 번 연속 실패해 몇 시간 동안 옛 커밋이 실행 중이었는데 CI는 성공으로 표시됐습니다. 코드 품질 검사가 실패했는데 job은 성공으로 끝나, 세 번 연속 아무도 알아채지 못했습니다.
- **재발 방지 조치**: 검사가 실패하면 job도 실패로 끝나게 했습니다. 배포 결과는 머지 후 실제 응답으로 확인합니다.
- **다시 발생하면**: 성공 표시 대신 [확인 주소](check-status.md#확인-주소)에서 실행 중인 커밋을 확인합니다.

## 로그와 배포 이력에도 잘못된 값이 남을 수 있다

- **사례**: 감사 로그의 접속지 주소가 늘 같은 값으로 기록됐습니다. 배포 이력에서 한 릴리즈 기록이 통째로 빠졌는데, 릴리즈 자체는 정상으로 보였습니다.
- **재발 방지 조치**: 로그에 기록되는 값을 테스트로 확인하고, 배포 이력은 성공 표시가 아니라 그 릴리즈의 기록이 실제로 있는지 확인합니다.
- **다시 발생하면**: 로그나 이력이 있다는 것만 보지 말고, 기록된 값이 실제와 맞는지 한 번 대조합니다.

## 필수 설정 값이 비어 있어도 서버가 시작될 수 있었다

- **사례**: 이미지 주소를 만드는 설정 값이 비어 있었는데 서버는 정상으로 시작됐고, 첫 업로드에서 오류가 났습니다.
- **재발 방지 조치**: 꼭 필요한 설정 값이 없으면 서버가 시작하지 않습니다.
- **다시 발생하면**: 새 환경을 만들거나 설정을 바꾼 뒤 특정 기능만 계속 실패하면 환경변수부터 확인합니다.

## 서버와 화면이 같은 판단을 따로 하면 결과가 달라진다

- **사례**: 서버는 허용하는데 화면이 막아 회의 안건을 쓰지 못했습니다. 완료한 업무가 화면에서만 «지연»으로 보였습니다. 접수 기간이 끝난 폼이 «접수 중» 탭에 남았습니다. 처리 시각이 아홉 시간 이르게 보였습니다.
- **재발 방지 조치**: 권한, 지연 여부, 접수 상태는 서버가 판단하고 화면은 그 결과를 그대로 보여 줍니다.
- **다시 발생하면**: 화면과 서버 응답이 다르면 서버 값을 기준으로 보고, 웹 쪽 이슈로 엽니다.

## 자체 시간 제한과 자원 부족으로 서비스가 멈출 수 있다

- **사례**: 규정 도우미가 자주 답하지 못했는데, Gemini 사용량 한도가 아니라 우리가 설정한 20초 시간 제한 때문이었습니다. 빌드 작업 두 개가 한 기기에서 동시에 실행되면서 메모리가 부족해져, 그 기기의 모든 서비스가 약 15분 응답하지 않았습니다.
- **재발 방지 조치**: 시간 제한 같은 값은 설정으로 드러내고 실제 측정값을 근거로 정합니다. 빌드는 한 번에 하나만 실행하고, dev 이미지는 GitHub Actions에서 빌드합니다.
- **다시 발생하면**: 시간 초과나 요청 거절이 나면 외부 서비스보다 우리 설정의 제한 값부터 확인합니다.

## dev에서 정상이어도 운영에서만 실패할 수 있다

- **사례**: 컨테이너용으로 켠 빌드 설정 때문에 운영 웹(Vercel) 빌드가 실패해, 한 릴리즈에서 서버만 배포되고 웹 세 앱은 옛 버전에 머물렀습니다. dev 웹을 컨테이너로 옮기자 세 앱 모두 로그인 후 잘못된 주소로 이동했습니다.
- **재발 방지 조치**: 한쪽 환경에만 필요한 설정은 환경변수로 나누고, 두 환경에서 모두 빌드해 확인합니다. 배포 환경을 옮기면 로그인과 링크 공유 카드부터 확인합니다.
- **다시 발생하면**: dev에서 문제가 없었다는 것만으로 운영도 괜찮다고 보지 않습니다. 릴리즈 후 세 앱의 `/version`이 모두 새 버전인지 확인합니다.

## 오류 응답을 남기지 않으면 원인을 찾기 어렵다

- **사례**: 배포 호출이 연달아 실패했는데 로그에는 종료 코드 하나만 남아, 원인을 네 번 잘못 짚었습니다. 같은 요청을 직접 보내 보니 응답 본문 한 줄에 원인이 적혀 있었습니다.
- **재발 방지 조치**: 요청이 실패하면 응답 코드와 응답 본문을 로그에 남깁니다. 비밀값은 값 대신 길이 같은 정보만 남깁니다.
- **다시 발생하면**: 추측으로 고치기 전에 실패한 요청을 직접 한 번 보내 응답 본문을 확인합니다.

## 접근 제한을 바꾸면 헬스체크도 실패할 수 있다

- **사례**: 로그인 없이 열리는 서버 주소를 두 개로 줄이자 dev 배포가 실패했습니다. Coolify의 헬스체크가 여전히 이전 주소를 사용하고 있었습니다.
- **재발 방지 조치**: 해당 주소를 사용하는 헬스체크, 외부 감시, 워크플로를 확인하고, 각 설정의 주소를 먼저 변경한 뒤 코드를 머지합니다.
- **다시 발생하면**: 보안 설정을 바꾼 직후 배포가 실패하면 헬스체크가 사용하는 주소부터 확인합니다.
